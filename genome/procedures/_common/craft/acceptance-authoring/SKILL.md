# acceptance-authoring

解析一个需求、要写出验收标准时用它。两件事:**每条怎么写才可判定**,以及**这次在哪一层验**。

## 一、可判定

一条验收标准是一句**能被一次执行判成真或假**的话。判据很简单:说得出"给什么、期望什么"
就可判定;说不出就不是标准,是愿望。

写不可判定的标准的代价不在你这一轮:出题人拿它出不出题,评审拿它对不上账,人工审批那一刻
只能凭感觉。而那时候纠正的成本比现在高两个数量级。

- 一条只说一件事。一句话里有"并且"通常是两条。
- 用需求方的词,不用实现的词。「库存扣减」不是「调用 `reserve()`」——后者把实现方式钉死了。
- 覆盖失败路径。只写成功路径的标准集,会让"没被验过"看起来像"验过了"。
- **id 是身份,顺序不是。** 它们会被下游按 id 引用(出题人的覆盖对应、评审的需求轴锚点),
  所以 id 一旦写出就别再改;顺序可以调,改 id 不行——改了之后所有引用都指向另一条,
  而没有任何东西会报错。

## 二、这次在哪一层验(测试缝)

**这件事没有别人替你回答。** 你不说,出题人只能自己猜一个;而缝选错的后果不是测试变红,
是测试写在了错的高度上:测太低,一次无害重构全红,下一个人学会的是"改测试";
测太高,真正的分支没人碰。

三条规矩:

1. **优先复用既有的缝。** 项目已经在某一层测了,就在那一层加。新开一道缝的成本是长期的。
2. **能取多高取多高。** 高的那道缝看到的是行为,低的看到的是结构。
3. **越少越好,理想是一条。** 一次改动跨了三道缝去验,通常说明这次的活该拆。

写法:在对应的验收标准里点明"在哪一层给什么、看什么"。拿不准就写进 `questions[]`,
附上你倾向的选项与理由——**猜一个缝出来,后面每一轮都在这个错误的前提上干活**,
而那个前提没有人会回头质疑,因为它看起来像是已经确定的事。

## 反例

- ❌ 「下单功能正常」 ← 判不了。什么输入?期望什么?
- ❌ 「性能有所提升」 ← 提升多少、在哪条路径上、拿什么量
- ❌ 「调用 `InventoryClient.reserve()` 并处理异常」 ← 把实现方式写成了验收标准,
  实现换个写法就"不达标",而行为其实没变
- ❌ 「下单成功后库存减少,并且失败时回滚,并且并发下不超卖」 ← 三条,拆开
- ✅ 「下单 3 件、库存 10 件 → 下单成功,该 SKU 剩余 7 件」
- ✅ 「下单 3 件、库存 1 件 → 下单失败,且该 SKU 剩余仍为 1(不产生预占记录)」
- ✅ 「缝:order-service 的服务层接口(既有用例已在这一层),不下探到仓储」

## 自检

- [ ] 每条都说得出"给什么、期望什么"
- [ ] 没有一条把实现方式当成了验收标准
- [ ] 失败路径至少有一条
- [ ] 每条只说一件事
- [ ] 说清了这次在哪一层验,而且优先用了既有的缝;拿不准的写进了 `questions[]`
